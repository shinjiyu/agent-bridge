# 注意力是稀缺资源

Vibe coding 之后，写代码不再稀缺。模型可以在一次对话里铺出几百行，也可以整段扔掉重来。稀缺的是你的注意力：你这一次看哪里、问什么、放过什么。

以前的编程和设计原则，几乎都是为另一个问题准备的。人要读这些代码，人要在半年后改它，人要把系统交给下一个同事。所以我们追求可读、可维护、分层、命名、小函数、少重复。那些原则没有错，它们服务的目标是：让人愿意把眼睛放在代码上，并且放得起。

目标变了，原则就不再适用。

现在大部分代码不是写给下一任维护者看的，是写给模型重写的。你若还按旧习惯把每一层都读顺、把每个名字都斟酌完，注意力就耗在模型随手能再生的东西上。可读性是给「人要长期握住这段实现」准备的。注意力管理是给「人只握判断，实现可以重来」准备的。这两件事不是同一门纪律。

## 注意力只够花在三处

学一个新东西，不学它具体是怎么做的。内部结构、调用链、框架典故，都是注意力的无底洞。先问三句，而且只问有证据的：

- 它能做什么
- 它不能做什么
- 做这件事的成本是多少：时间、钱、返工、以及做错的风险

这三句就是注意力该落下的地方。能做，决定你把任务交给它。不能做，决定你不把命交给它。成本，决定这件事值不值得做。三句都答不上来，就不要往下学实现。

## 提问是在分配注意力

注意力不会自己落对地方。你问什么，你就在看什么。

问「这段怎么实现的」，注意力进了机制，出来时你懂了一点结构，仍不知道该不该用。问「它能不能做 X，做不成时长什么样，要花多少」，注意力停在边界上。下一句该问的，是你刚才没看住的那个风险，不是模型刚生成的那个函数。

不会提问的人，在 vibe coding 里不是学得慢，是把整份注意力交给了模型的默认输出。模型擅长把场面填满。场面填满的时候，人最容易觉得自己在干活。

## 旧原则什么时候还留着

不是每一行都该当一次性的。你自己要长期握住的那一小段——钱、权限、安全边界、你签过字的契约——仍然要人能读懂。那里继续讲可读、可维护。

除此之外，为可维护性付注意力，是在用旧时代的税，给一个可以整段重写的草稿。结构服务于一件事：让你少看。测试、接口、失败样例，是注意力的锚；不是为了让代码看起来像一本教材。

先管住注意力，再谈怎么写。
